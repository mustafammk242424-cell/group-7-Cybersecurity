## **1. Introduction**
Threat modeling is a structured process used to identify, quantify, and address security risks associated with a system. For our Topic 15 project, the demonstration system consists of two primary components: the **OWASP Juice Shop** (deployed via Docker) serving as the modern vulnerable target, and custom **Python Flask modules** designed to demonstrate specific OWASP Top 10: 2025 vulnerabilities (e.g., A10: Mishandling of Exceptional Conditions). This report utilizes the **STRIDE** threat modeling methodology to analyze potential attack vectors and map them to corresponding remediation strategies.

## **2. System Architecture & Data Flow Diagram (DFD)**
To perform threat modeling, we first define the system boundaries and data flows. 

### **2.1 System Components**
1.  **External Entity (User/Attacker):** Interacts with the system via a web browser (e.g., Firefox, Chrome).
2.  **Process 1 (OWASP Juice Shop):** A Node.js/Angular application handling e-commerce logic, user authentication, and product reviews.
3.  **Process 2 (Custom Flask Module):** A lightweight Python application specifically hosting the A10 Fail-Open/Closed demonstration endpoints.
4.  **Data Store (Database):** SQLite/PostgreSQL database storing user credentials, product data, and review comments.

### **2.2 Level 1 Data Flow Description**
*   **DFD-1:** User sends HTTP Request (Login credentials, XSS payload, or SQLi payload) $\rightarrow$ Web Server (Juice Shop/Flask).
*   **DFD-2:** Web Server processes request $\rightarrow$ Queries Database (SQL execution).
*   **DFD-3:** Database returns data $\rightarrow$ Web Server formats response $\rightarrow$ User Browser renders HTML/JavaScript.

## **3. Threat Analysis using STRIDE Model**
We apply the STRIDE model (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) to the identified data flows and components.

| STRIDE Category | Threat Description | Affected Component / DFD | OWASP Top 10: 2025 Mapping | Risk Level | Mitigation / Remediation Strategy (Blue Team) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Tampering** | **SQL Injection (SQLi):** Attacker injects malicious SQL payloads (e.g., `' OR 1=1--`) into login fields to manipulate database queries. | DFD-1, DFD-2 (Input fields $\rightarrow$ DB) | **A05: Injection** | **High** | **Remediation:** Use Parameterized Queries or ORM (e.g., Sequelize in Node.js). Never concatenate user input directly into SQL strings. |
| **Tampering** | **Cross-Site Scripting (XSS):** Attacker injects malicious scripts (e.g., `<img src=x onerror=alert('XSS')>`) into review fields, which are stored and executed in victims' browsers. | DFD-1, DFD-3 (User Input $\rightarrow$ Browser) | **A05: Injection** | **High** | **Remediation:** Implement strict Input Validation and Output Encoding. Use libraries like DOMPurify to sanitize HTML. Set `Content-Security-Policy` (CSP) headers. |
| **Elevation of Privilege** | **Fail-Open Vulnerability (A10):** When the backend database crashes or throws an unhandled exception during an authorization check, the system defaults to `return True` (Access Granted) instead of blocking the request. | Process 2 (Flask Module `/admin` endpoint) | **A10: Mishandling of Exceptional Conditions** | **Critical** | **Remediation:** Implement **Fail-Closed** mechanisms. In `try-except` blocks, the `except` clause must default to denying access (e.g., return HTTP 503 and "Access Denied"). |
| **Spoofing / Tampering** | **Dependency Confusion (Supply Chain):** Attacker publishes a malicious package with the same name as an internal library to a public registry (npm/PyPI). The build system pulls the malicious package. | Process 1 & 2 (Build/Deployment phase) | **A03: Software Supply Chain Failures** | **High** | **Remediation:** Use Software Bill of Materials (SBOM). Pin dependency versions. Use private registries and verify package signatures. |
| **Information Disclosure** | **Verbose Error Messages:** The application returns detailed stack traces to the user when an error occurs, revealing internal file paths, framework versions, and database schemas. | DFD-3 (Server $\rightarrow$ User) | **A02: Security Misconfiguration** | **Medium** | **Remediation:** Disable debug mode in production. Implement global exception handlers that return generic error messages (e.g., "An unexpected error occurred") to users, while logging details internally. |
| **Elevation of Privilege** | **Broken Access Control (IDOR):** Attacker changes a URL parameter (e.g., `/api/users/123` to `/api/users/124`) to access another user's private data without proper authorization checks. | DFD-1 (API Endpoints) | **A01: Broken Access Control** | **High** | **Remediation:** Implement strict server-side authorization checks for every request. Use a "Deny by Default" policy. Do not rely on client-side hiding of UI elements. |

## **4. Risk Prioritization & Focus for Demonstration**
Based on the STRIDE analysis, our demonstration system will prioritize the following high-risk areas for the Phase 2 Product:
1.  **A10: Mishandling of Exceptional Conditions:** This is a new and critical category in OWASP 2025. Our custom Flask module will explicitly demonstrate the transition from a vulnerable **Fail-Open** state to a secure **Fail-Closed** state.
2.  **A05: Injection (SQLi & XSS):** As the most prevalent vulnerabilities, we will use OWASP Juice Shop to demonstrate the attack and then showcase the remediated code (Parameterized Queries and DOMPurify).
3.  **A03: Supply Chain:** We will integrate a lightweight dependency scanning tool (e.g., `pip-audit` or `npm audit`) into our demonstration dashboard to show how to detect vulnerable components.

## **5. Conclusion**
This threat modeling exercise confirms that the proposed demonstration system effectively covers the most critical risks outlined in the OWASP Top 10: 2025. By combining the comprehensive vulnerabilities of OWASP Juice Shop with targeted custom Flask modules (specifically for A10), the project provides a holistic view of both **Detection** (Red Team) and **Remediation** (Blue Team) strategies.
